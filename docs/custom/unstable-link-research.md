# 変動・詰まり・短い切断への対策調査

調査日：2026-10-15（日本時間）。対象はWindows Sunshine Custom、Mac/iPad等のMoonlight、250kbps〜1Mbps前後の不安定回線。現在のコードは9a7fda75。最低2周という依頼に従い、1周目に複数方式の候補を集め、2周目に逆効果になる条件・通常Moonlightとの互換性・現行コードへの適用を確認した。

## 結論

優先する組み合わせは、実際の総送信量の予算化、回線に応じた送信ペーシング、時刻に基づくキュー制限、接続中の適応制御である。背景を粗くするだけではパケットの集中・最低FECコスト・古い画像の滞留を解決できない。画面処理はこれらと併用する。

完全に通信できない間の遠隔操作は維持できない。その間は最後の画像を保持し、復帰後に古い画像・古い操作を順に実行せず、現在の状態へ復帰する設計を目指す。

今回、新しい回線制限・障害注入試験は実行していない。稼働中の配信やネットワーク設定を変更せず、公式資料・コード・以前の試験記録を調査した。以下の制御値と実装順は提案であり、検証済みの性能保証ではない。

## 2周目：症状別の効果と逆効果を確認

| 症状 | 第一候補 | 併用候補 | 限界・避けること |
| --- | --- | --- | --- |
| 回線速度が徐々に下がり遅延も増える | 総送信量を下げる適応制御 | ペーシング、背景低頻度化、符号化前のFPS制限 | FEC増量だけで直そうとすると混雑が悪化する |
| 平均量は小さいが時々まとめて詰まる | 送信ペーシング、IDR等の大きなフレームの抑制 | エンコーダのVBV、必要に応じたintra refresh | 平均ビットレートだけ見ない。毎回エンコーダを作り直さない |
| 遅延は安定しているがランダムな損失がある | 回線予算内のFEC | 短いRTTなら期限付き再送という別方式も候補 | RTPの任意再送は現行Moonlightに追加が必要。補正を無制限に増やさない |
| Wi-Fi等で到着間隔が揺れる | 小さく上限のある受信バッファ | 有線・電波条件の改善、ローカルカーソル | バッファを大きくするほど操作結果の表示が遅れる |
| 数百ms〜数秒、通信が完全に止まる | 映像保持、不要な送信を止める、復帰時に現在状態へ戻す | 接続・復旧状態管理、入力状態のリセット | 通信不能の間は操作できない。失敗した古いクリックを勝手に再送しない |
| 他のダウンロード・ファイル転送時だけ遅い | SQM/AQMと総量制限 | 制御優先、ファイル転送一時停止 | OSの優先度だけではISPやWi-Fi内のキューを消せない |
| ネットワーク統計は正常なのに画面が止まる | GPU・デコーダ・描画キューの計測 | エンコード負荷・実FPSの調整 | ネットワークが原因と決めつけない |

2周目で特に確認したこと：

1. **FECと再送は別の対策。** RFC 8854では補正込みの総量を予算内に収める必要があり、混雑による損失へ補正を追加すると悪化し得る。再送は追加の往復時間が必要で、RTTが表示期限より長い時に対話用映像を救えない。
2. **ペーシングだけでは帯域不足を解決しない。** 発生量が送信可能量を超えれば自分のキューが溜まる。WebRTCのペーサーもキュー上限に応じて送信速度を増やす場合があるため、その実装を単純に移植して総量上限と呼ぶことはできない。
3. **古い圧縮フレームは自由に捨てられない。** Pフレームには参照依存がある。符号化前の生画像を間引く方法を優先し、符号化後に破棄する場合は参照無効化やIDR復旧と一緒に設計する。Moonlightにもデコードキュー溢れ時のIDR要求処理がある。
4. **FPS低下は映像予算変更と組み合わせる。** 同じエンコードビットレートを保ったままFPSだけ下げると、1フレームが大きくなることがある。FPS低下はパケット・最低FECコストの削減には役立つが、エンコーダ目標値も下げる必要がある。
5. **静止画の受信量は回線容量ではない。** 送る内容が少ないだけの状態を「回線が遅い」と学習しない。低負荷時の安易な容量推定・高負荷の速度テストを避け、受信情報と遅延傾向を合わせて判断する。
6. **可変回線では固定SQM設定にも限界がある。** 実回線が設定値を下回ると上流にキューができる。cake-autorateは負荷と遅延に基づいてシェーパー値を調整する実装例だが、管理可能なルーターが必要で、回線断自体を解消しない。
7. **NVENCには再設定APIがあるが現行の自動制御ではない。** NVIDIAはセッションを破棄せず設定変更するAPIを提供する。Sunshine側のSDK共通インターフェイスへ追加し、各SDK/エンコーダの対応を検証する必要がある。
8. **別通信方式への置換はクライアント互換性に影響する。** QUIC DATAGRAMは損失時に再送しないが、それだけで容量推定・優先制御が完成するわけではない。SRTは再送用の待ち時間を要する。いずれも標準Moonlightへそのまま挿し替えられない。

## 現在のカスタム版で確認した制約

- [送信ペーシング](D:/data/code/sunshineCustom/src/stream.cpp:1733)は約800Mbpsを基準とする。250kbps〜1Mbpsを基準にした送信配分ではない。
- [パケット構成](D:/data/code/sunshineCustom/src/stream.cpp:1674)にはRTP/FEC等が含まれる。指定された映像ビットレートと実際のIP転送量は一致しない。
- [FEC最低数](D:/data/code/sunshineCustom/src/stream.cpp:868)を満たすために補正パケットを増やす。クライアント側の[SDP](D:/data/code/moonlightCustom/moonlight-common-c/moonlight-common-c/src/SdpGenerator.c:211)は最低2個を要求する。少量のフレームではFEC設定を20%から5%へ下げてもパケット数が変わらない場合がある。FEC=0の現行経路は別条件だが、損失への耐性を失うため単独の推奨策にはしない。
- [静止画の最低FPS](D:/data/code/sunshineCustom/src/video.cpp:2436)は未指定なら要求FPSの半分。要求30fpsなら約15fpsの再送出が発生し得る。最低FPSを下げても動く画面のFPS上限は下がらない。
- [safe::queue_t](D:/data/code/sunshineCustom/src/thread_safe.h:412)には既定32個・古い要素を落とす制限がある。ただし個数制限は時間制限ではない。低FPSや送信停止では古い画像が長く残り得る。
- 映像送信は[共通ブロードキャストワーカー](D:/data/code/sunshineCustom/src/stream.cpp:1598)を使う。単純に長くsleepする低速ペーサーを追加すると、他の接続の送信も待たされ得る。複数接続では接続ごとの送信予定時刻とPC全体の上り予算を持たせる。
- [損失統計処理](D:/data/code/sunshineCustom/src/stream.cpp:1230)はログ中心。新しいMoonlightにはFEC状況報告もあるが、世代・送信条件が異なり、受信パケットの全到着時刻やデコード待ちが常にホストへ届くわけではない。
- 現在の自動背景設定と音声停止は接続開始時の選択であり、接続中の実回線変動に追従する制御ではない。
- マウスが配信モニター外・位置不明の時、現在の画像処理は全画面の通常サンプリングへ戻る。将来のモニター別同時配信では、操作していない画面の背景保持も検討対象になる。
- NVENCの[共通インターフェイス](D:/data/code/sunshineCustom/src/nvenc/nvenc_encoder.h:27)には現状、動的ビットレート再設定の公開メソッドがない。

### 最低送信コストの例

仮に1フレームがデータ1個＋補正2個、各IPパケット1400バイトなら、映像だけで必要量は以下となる。これは計算例であり、現在の全接続の正確な下限ではない。パケットサイズ・フレームサイズ・FEC無効化・経路などで変わる。

| 実送出FPS | 最小3パケットの例 |
| --- | ---: |
| 30 | 1008kbps |
| 15 | 504kbps |
| 10 | 336kbps |
| 5 | 168kbps |

計算はFPS × 3 × 1400 × 8。音声・制御・Ethernet・VPN分は別に必要になる。音声OFF・背景1/16でも、FPSと最低FECコストが合わなければ250kbpsへ収まらない。

また64KiBのデータを一度に渡す例では、250kbpsの区間を通過するだけで約2.10秒、1Mbpsでも約0.52秒かかる。大きなフレームや一括送信を平均値だけで評価しない理由である。

## 提案する実装順

1. **計測を追加する。** 総IP送信量、FEC・パディング内訳、100ms/1秒ピーク、送信待ちの最古時刻、RTT基準値と増分、フレーム損失、IDR/RFI回数を接続ごとに記録。クライアントはネットワーク損失とデコード・描画待ちを分ける。
2. **総量を予算化し、ペーシングと生成側抑制を同時に実装する。** エンコード量だけではなくFEC・ヘッダー等を数える。入力・制御を先に通し、ファイル転送は残余帯域で一時停止可能にする。動画キューを時間で制限し、符号化前の古い画像を間引く。複数接続はPC全体の予算内で配分する。
3. **接続中の適応状態を追加する。** 通常→混雑→回復→短い切断の状態を持つ。悪化時は映像目標・実FPS・背景周期を下げ、回復時は小幅に上げる。基準RTT・揺れを考慮し、切り替えの連発を防ぐ。保存設定を書き換えず、エンコーダスレッド内で反映してサーバー再起動を避ける。
4. **FECと復旧を適応させる。** 損失と遅延増加を区別し、補正込み予算内で調整する。IDR要求をまとめ、回復時の大きなフレームで再び詰まることを防ぐ。intra refreshは復旧速度・画質・GPU/コーデック対応を検証して選ぶ。
5. **短い停止からの復帰を扱う。** 送信不能時に待ち行列を増やさず、最後の画面を保持する。復帰後は現在の画面へ同期する。入力の押下・解放は整合を取り、クリックや古いキー入力を後追い実行しない。接続維持にはホスト・クライアント双方のタイムアウト確認が必要。
6. **必要な場合にクライアントを拡張する。** 到着時刻・実受信量・デコード待ちを報告し、ローカルカーソルや復帰UIを追加。通常Moonlightでできる範囲のホスト改善を先に進める。

通常Moonlightへの互換性を維持できる候補は、既存形式のペーシング・符号化前間引き・映像予算変更・背景処理・既存FEC形式での調整。新しい統計報告、ローカルカーソル同期、QUIC/WebRTC/SRTへの置換は、機能・実装によってクライアントの追加対応が必要になる。全OS・全版の互換性は実接続で確かめる。

## 検証条件案

稼働中の接続に障害を注入せず、別ポート・専用VM/ネットワーク等に隔離して実施する。Moonlightは必ずウィンドウモード。netem等で帯域・遅延・損失を別々に再現する。

| 条件 | 内容 |
| --- | --- |
| 固定帯域 | 1000、500、250kbps |
| 速度変動 | 1000→250→500→1000kbps、段階的に切り替え |
| ランダム損失 | 同じ帯域で0%、1%、3%、5% |
| バースト損失 | まとまった短い損失を、平均損失率とは別に評価 |
| 到着の揺れ | 同じ基準RTTにジッター・順序入替を追加 |
| 高RTT | 混雑なしの高RTTと、キュー増加による高RTTを区別 |
| 短い切断 | 300ms、1秒、3秒の通信停止と復帰 |
| 競合通信 | 同時ファイル転送・別アプリ通信 |
| 複数接続 | 同じPC上りを2クライアントで共有 |

画面は静止文字、スクロール、ウィンドウ移動、マウス移動、パーティクルを分ける。比較する実装は現行、ペーシング、適応予算＋ペーシング、時間制限＋符号化前間引き、FEC調整の段階とする。静止画だけで速度推定を誤らないことも確認する。

見る指標は平均/ピークのIP総量、操作→表示遅延の中央値・95/99パーセンタイル、フリーズ時間、復帰時間、画面の古さ、読みやすさ、FEC回復/未回復フレーム、IDR量、デコード・描画待ち、接続継続、入力状態。ループバックの処理時間だけでネットワーク品質を評価しない。

合格基準の具体値は計測後に決める。最低限、回復後に古い画面が何秒も順に再生されないこと、入力が取り残されないこと、総量が制限に収束すること、他の接続を止めないこと、対策なしより95%操作遅延とフリーズを改善することを確認する。
