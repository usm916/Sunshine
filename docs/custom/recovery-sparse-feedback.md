# 回線回復後も背景が粗いまま残る問題

2026-10-15、低帯域制御・プロファイル適用・GPU背景キャッシュの3箇所を確認した。

## 再現と原因

500msごとの計測窓に新しい制御応答がなければ、毎回「健全な状態が続いている時間」をリセットしていた。
1秒ごとに正常な応答が届く模擬経路では、交互の窓が空になるため回復の10秒条件に達しない。
実際のC++コントローラーの回帰テストで、1000kbpsから750kbpsへ低下後、正常な応答を1秒ごとに60秒与えても
750kbps、背景1/12・3秒更新から戻らないことを確認した。
これは再現したコード上の原因であり、ユーザーの実回線ログで全事象を確定したものではない。

## 修正

短い応答間隔の空きだけでは回復タイマーをリセットしない。
2秒以上の制御応答途絶、損失、RTT上昇、送信予算超過、不正な報告、計測の大きな空きは従来どおり回復を止める。
上方への試行は、実際に新しい応答と正のRTTが届いた時だけ行う。無通信を回復の根拠にしない。

既存の10秒安定後・約2秒ごと5%増加という慎重な回復を保ち、クライアントの要求上限まで段階的に戻す。
全体の映像サイズは変えず、背景の粗さ・更新周期とFPSが予算に応じて戻る。
急激な帯域増加や常に即座に鮮明になることを保証する変更ではない。

背景キャッシュは加工前の画素を保持する。より細かい設定への変更はその画素を再サンプリングし、
3Mbps以上では加工を解除して現在の入力画素を使う。粗く加工した画像を保持し続ける構成ではない。

## ログの見方

`low_bandwidth_decision` の `direction=recover` と `wire_kbps` の上昇を見る。
続く `low_bandwidth_apply` で `result=applied` または `unchanged`、`background_scale`、
`background_loop_ms`、`focus_enabled` を見る。背景設定が戻っているかを数値で追跡できる。
`result=failed` 等の場合はエンコーダーの再設定側の問題として切り分ける。
ログ中の認証ヘッダーや証明書を共有する必要はない。

修正後は正常な応答が1秒おきでも1000kbps・背景1/4へ回復した。設定適用とGPU描画も粗い状態から細かい状態へ戻すテストで確認した。ネイティブ369件、Web UI 72件成功。
