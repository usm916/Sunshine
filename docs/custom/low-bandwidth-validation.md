# 低帯域モードの検証記録

検証日: 2026-10-15。Windowsホスト、ネイティブNVENC、HEVC、2560×1440、要求30fps。
クライアントはすべてウィンドウモード。稼働中の既存Sunshineは変更せず、試験用ホストを別ポートで起動した。

## 観点1: コードとプロトコル

PR #5460の計測・NVENC再設定基盤を取り込み、別の低帯域制御を追加した。
既存の3Mbps下限を250kbps〜1Mbpsの制御へ適用せず、接続別の上限・下限で動かす。
通常の映像パケットとフレーム番号を維持し、エンコード前に生成を間引く。
NVENCのFPSとビットレートを一緒に再設定する。失敗時は最後に成功した設定を保持する。
低帯域モードでは、FEC報告がない計測窓も定期的に処理する。

音声送信を停止し、マウス優先の矩形/円形・幅・高さを保ちつつ背景の粗さと更新周期を予算へ連動させる。
再設定のたびにホストを再起動したり、配信を接続し直したりする処理は入れていない。

## 観点2: 自動テスト

- ネイティブの対象テスト168件成功。低帯域制御、FPSゲート、NVENC再設定、通信計測、背景キャッシュ、既存クリップボード、設定整合性等。
- Web UI全70件成功。LowBandwidth.vueは行11/11・分岐2/2・関数4/4を通過。
- 低帯域制御ヘッダーvideo_low_bandwidth.hの実行可能行75/75を通過。変更全体の網羅率が100%という意味ではない。
- 1000→250→1000kbpsへ変化する合成トレースで減速・回復と上下限を確認。
- 古い制御情報、不正通知、再設定失敗、FPSだけの変更、VBVとFPSの連動を確認。
- MSYS2 UCRT64でsunshineとtest_sunshineをビルド済み。NVENC SDK 11/12/13/13.1用実装を含む。
- build-sunshine.shの構文検査成功。clang-formatの更新後に無関係な変更がないことを確認。

作業ツリーの記録はcmake-build-custom/low-bandwidth-tests.logとlow-bandwidth-web-all.logにある。

## 観点3: 実接続とパケット計測

ローカルのループバックで接続し、Wiresharkのdumpcap/tsharkで8秒間の映像UDPを計測した。
帯域制限器を通したWAN試験ではない。デスクトップの内容は固定せず、画質の公平な比較試験には使えない。
映像IP通信量はip.lenの合計。FECとIP/UDPヘッダーを含むが、制御通信、VPN、リンク層の再送を含まない。

| クライアント | 初期映像経路予算 | コーデック目標 | エンコード上限 | 観測映像IP | 観測RTPフレーム/秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Moonlight Custom / Fixed | 250kbps | 92kbps | 4fps | 163.704kbps | 3.625 |
| Moonlight Custom / Fixed | 500kbps | 196kbps | 8fps | 300.124kbps | 7.625 |
| Moonlight Custom / Fixed | 1000kbps | 497kbps | 10fps | 590.196kbps | 9.25 |
| 通常版Moonlight 4.3.1 / Fixed | 250kbps | 92kbps | 4fps | 172.320kbps | 3.875 |

通常版はクライアント設定500kbps、ホスト上限250kbpsで接続した。
上の値は実測区間の平均であり、常にこの通信量になることや瞬間上限を保証しない。
どの計測でも音声UDPは0パケットだった。

### 停滞・復帰

試験用に起動したクライアントだけを、映像受信開始後に4秒間停止し、必ず再開した。
パケット損失・速度制限・RTT遅延を独立に注入した試験とは異なり、受信処理と制御応答の停滞を模擬する。

- Custom: 初期500kbps/8fps → 375/6 → 281/4 → 210/3 → 157/2 → 117/2 → 100/2。NVENC適用はすべてapplied。
- 通常版4.3.1: 初期375kbps/6fps → 281/4 → 210/3 → 157/2 → 117/2 → 100/2。
  安定後は108、116、124…と増加し、180kbps/3fps、198kbps/3fpsまで回復を確認。
- 通常版は500kbpsを選択してもホストへは375kbpsの映像要求を送った。この旧版では低い要求を尊重して開始した。
- 自動調整の前後で試験用ホストのPIDは不変。クライアントも終了せず、通常版の終了時統計ではデコード・描画の継続を確認した。
- 受信再開時に通常版でデコードキューあふれとIDR要求が発生した。その後の復帰は確認できたが、無瞬断や無劣化を意味しない。
- 停止を模擬した後の観測はCustom約66.056kbps/2fps、通常版約116.316kbps/2.25fps。
  通常版の計測中は自動回復が続いていたため、固定予算の比較値ではない。

機械可読のローカル記録はcmake-build-cursor-focus-live/low-bandwidth-adaptive-results.jsonと
low-bandwidth-official-results.json。初期の固定試験結果はcmake-build-custom/low-bandwidth-live.logにある。
試験用認証情報とパケットキャプチャは配布物へ含めない。
