# 移動回線での回復停止修正（2026-10-18）

対象はWindows/NVENCの低帯域自動モード。設定場所は **Sunshine Web UI → Configuration → Audio/Videoタブ → Low bandwidth mode → Adaptive bitrate, FPS and background**。

## 変更内容

- 送信量は500ms単窓から、実測時間で重み付けした3秒の移動平均へ変更。1fpsで送信の山と空の窓が交互に来ても、一瞬の山だけで回復待ち時間をリセットしない。過剰送信の判定は3秒の履歴がそろってから行う。予算を下げた直後は古い予算で送った履歴を捨てる。欠落や制御応答の停滞による減速は従来どおり。
- RTTの基準は永久固定をやめ、最小RTT観測から30秒以上経過し、遅延による減速を試した後（または最低予算に到達後）に、10秒以上の清浄で安定したRTTを確認できれば、その期間の最小値へ更新する。
- 基準更新には新しい正の制御RTT、継続した観測、3秒の送信量平均が現在予算以下、欠落・FEC回復・不正報告がないことを要求する。RTTの候補範囲はmax(10ms, 候補最小値の25%)以内。無応答、持続する損失、送信量超過、変動の大きいRTTは更新の根拠にしない。
- infoログへ `low_bandwidth_state` を追加。理由や基準更新等の状態変化時に出力し、最大でも2秒に1回。同じ状態で定期的にログを書き続けない。

速度テストや新しいネットワーク通知、Moonlightの変更は追加しない。固定長の小さな履歴を使い、制御処理でヒープ確保しない。

## 診断ログ

ログの場所は **Sunshine Web UI → Troubleshooting（トラブルシューティング）→ Logs**。

`low_bandwidth_state` の主な項目：

| 項目 | 意味 |
| --- | --- |
| `wire_kbps` | 現在の要求予算 |
| `sender_average_kbps` / `sender_window_ready` | 3秒移動平均／履歴完成 |
| `rtt_ms` / `baseline_rtt_ms` | 現在の制御RTT／採用中の基準 |
| `baseline_revision` | 安定した新経路の基準を採用した回数 |
| `healthy_ms` / `ack_age_ms` | 健全期間／新しい正のRTT観測からの経過 |
| `hold_loss` / `hold_latency` / `hold_stalled` | 欠落／遅延増加／応答停滞 |
| `hold_sender` / `hold_unreliable` / `hold_sampling_gap` | 継続的な予算超過／信頼できない報告／観測間隔の空き |
| `adaptation_stopped` | エンコーダー再設定失敗・非対応で調整が停止 |

`low_bandwidth_decision direction=recover` と、続く `low_bandwidth_apply result=applied` または `unchanged` も確認する。診断ログは帯域測定値ではなく、送信量と制御器の判定である。

## 今回の範囲と限界

今回の実装は監査の優先事項である送信量集計、RTT基準更新、診断ログ。回復速度の10秒安定後・約2秒ごと5%または8kbps増加と、エンコーダー再設定失敗後の停止方針は維持する。100kbpsまで下がった後に必ず1分以内で粗粒化を解除する変更ではない。粗粒化解除は従来どおり3000kbps以上。

実際の列車移動での再確認は未実施。接続先・要求上限・実RTT・欠落・ログを合わせて確認する。[変更前の監査](mobile-link-recovery-audit-2026-10-18.md)の5件は当時の問題を観測する監査テストで、修正後の成功判定には正式な回帰テストを使用する。

## 別PCへ適用する場合

1. Sunshine Customの配置先と現在の版をバックアップする。
2. **Windowsのサービス → Sunshine Custom → 全般タブ → 停止**。sunshine.exeが終了してから更新する。
3. 修正版ZIPを、サービスが登録されている既存packageフォルダーへ上書き展開する。設定・秘密鍵・ペアリングはZIPへ含めない。
4. **Windowsのサービス → Sunshine Custom → 全般タブ → 開始**。Moonlightを再接続する。

配置先を変えなければサービスの再登録は不要。実行中のexeを上書きしない。更新失敗時はサービスを停止してバックアップ一式を戻す。

ビルド・正式テスト・カバレッジ・配布物の結果は `cmake-build-recovery-fix/` に記録する。起動中ホストの差し替えと別PCへの適用は、それぞれの実施記録を確認する。

## 今回の検証結果

- 正式な関連ネイティブテスト409件／51スイートが成功、失敗・スキップ0。
- 製品コードの変更実行行は制御ヘッダー84/84、接続処理20/20。合計104/104行を実行。これは変更箇所の行カバレッジであり、全分岐・プロジェクト全体の100%ではない。
- 独立した制御テスト23件も成功。1fpsでの平均予算以下の送信の山、安定した高RTTの新経路、疎な新規ACK、持続損失、不正報告、送信過多、RTT変動、境界値とログ抑制を検証。
- カスタムMoonlightをウィンドウモードで隔離した127.0.0.1の試験ホストへ接続し、受信側を4秒停止。同じホスト・接続で4000→168kbpsの減速後、45秒の観測で176→295kbpsへ回復を開始した。診断ログも出力された。実回線の制限試験ではなく、粗粒化解除まで実接続で確認した結果でもない。
- 修正版配布一式は `cmake-build-custom/package-recovery-fix-20261018`、ZIPは `cmake-build-custom/Sunshine-recovery-fix-20261018-windows-x64.zip`。166ファイルの一致とZIPのCRCを確認した。
- 2026-10-19に常用先 `cmake-build-custom/package` へ適用し、サービスを再起動した。実ホストID・証明書の一致と既存のMoonlight登録保持を確認。[適用記録](tan-update-2026-10-19.md)。


## 本体だけの部分更新

現行TAN版とはDLL・サービスラッパー・Web画面・シェーダーが同一のため、実行時の差し替えは `sunshine.exe` だけで済む。版情報と説明書を添えた部分更新ZIPを用意した。[対象版・PINの保持・停止から再開までの手順](binary-update.md)を参照。
