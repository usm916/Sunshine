# VNCの低帯域・不安定回線への対応とSunshineへの応用

調査日: 2026-10-15。対象: Windows Sunshine Custom、iPadを優先した通常Moonlight、
250kbps～1Mbps程度の回線。ソフトの導入、ホスト再起動、回線制限試験は行っていない。
仕様、実装、適用条件を異なる3観点で検証した。実接続を3回再現した性能試験ではない。

## 結論

VNCから学ぶべき点は、変更箇所の追跡、更新の集約、混雑時に新しい更新を作りすぎない制御、
ローカルカーソル、画面が静止してからの画質回復である。
デスクトップの文字入力・局所的な更新では効果が見込めるが、全画面動画・パーティクルで
VNCが必ずSunshineより少ない帯域になるとは言えない。

H.264/HEVCもフレーム間予測で変わらない画素を効率よく符号化する。
「VNCだけが差分を送れる、Sunshineは全画素を毎回送る」という比較は誤り。
重要な違いは、VNCではクライアントが画面を保持し、矩形単位の更新を受け取るモデルで、
通常Moonlightでは動画コーデックのフレームと参照関係に従って画面を復元する点にある。

## 1周目: RFB仕様を検証

[基礎仕様 RFC 6143](https://www.rfc-editor.org/rfc/rfc6143.html)から確認した要点:

- 画面更新は矩形列。クライアントは以前の画像を保持し、更新部分を書き換える。
- incremental要求は変更分を対象とし、変化がなければ返答まで長く待てる。
- 基本モデルはクライアントからの更新要求に応じる。遅い端末・回線では更新頻度が下がり、
  同じ場所の途中状態を省いて通信量を減らせる。
- CopyRectは、既にクライアントにある領域を移動して利用する指示。スクロール等で活用できる。
- Cursor拡張は形状・ホットスポット等を送り、クライアントでカーソルを描く。
- 通常はTCP等の信頼性のある通信を使う。

節3、7.5.3、7.6.1、7.7.2、7.8.1を照合した。
CopyRectは常に使用できるわけではなく、両端の画像状態と操作の対応が必要。
マウス周囲を自動的に最優先にする処理まで、RFB基礎仕様が規定しているわけではない。
Continuous Updates等の拡張では、毎回の要求を待つ方式から動作が変わる。

## 2周目: 代表実装のコード・設定を検証

コード参照を固定したリビジョン:

- TurboVNC: ce9585becd8bed42ea568aea1781d704ec9e2a53

確認に使用した原本のコピーは cmake-build-vnc-research/sources に保存した。
以下は全VNC製品の共通機能ではなく、各実装で確認した内容。

### TigerVNC

| 処理 | 確認した実装 | 効果・限界 |
| --- | --- | --- |
| 本当に変更された領域の絞り込み | ComparingUpdateTracker::compare / compareRect。前の画面と画素比較し変更領域を縮める | 単なる再描画通知でも同じ画素なら送る範囲を減らせる |
| 内容ごとの圧縮方式 | EncodeManager::writeSubRectで色数・連続性を解析。単色、2色ビットマップ、パレット、フルカラーを選ぶ | 文字・UIの少色領域と写真等を使い分ける。文字を意味解析しているわけではない |
| Tight圧縮 | TightEncoder::writeRect / writeSolidRect。単色塗りつぶし、2色、パレット、zlib圧縮 | 少色パレット自体は元の画素を保存できる。色数を減らす画質設定とは別 |
| JPEG利用 | EncodeManagerがTight JPEG等の対応エンコーダを選ぶ | 写真・多色領域に有効だが文字のにじみ等もあり得る |
| 受信速度に基づく自動変更 | CConn::framebufferUpdateEnd、updateQualityLevel、updatePixelFormat | 更新受信中の速度を平滑化して設定変更。回線容量の正確な測定や厳密な帯域上限ではない |
| 混雑時に新規送信を保留 | VNCSConnectionST::isCongested / writeFramebufferUpdate | 送信バッファが残っていれば待つ。Fence対応ならRTT等に基づく窓の制御も使う |
| 画質回復 | EncodeManager::handleTimeout / writeLosslessRefresh | 最近変化しなくなった劣化領域を追跡し、鮮明な更新を後から送る |
| 回復更新の量を制限 | VNCSConnectionST::writeLosslessRefresh | 推定帯域と次回更新までの時間から予算を計算。実装内の圧縮率推定は概算で、厳密なbps保証ではない |

固定リビジョンのCConnでは、推定受信速度が256,000bpsを超えないとフルカラーから低色数へ切り替える。
JPEG品質の自動選択もあり、16Mbpsを境に品質レベル8/6を選ぶ。
これらはこの実装の閾値であり、250/500kbps専用の精密な適応ビットレート制御ではない。
公式viewer設定には低色数8/64/256色の選択もある。
旧プロトコルとの安全性のため自動色形式変更を制限する経路がある。

Congestionクラスは、TCP上のアプリ層で遅延増加に基づくVegas系の制御を行う。
基準RTTと観測RTT、送信量・受信処理確認を使い、送信中データの窓を縮める。
Fence非対応クライアントでは同じ追加制御を使えず、送信バッファとTCP側の制御等に依存する。
画面更新がないことと端末が死んでいることは別に扱われるが、認証・無操作等のタイムアウトは存在する。

### TurboVNC

[公式性能資料](https://github.com/TurboVNC/turbovnc/blob/ce9585becd8bed42ea568aea1781d704ec9e2a53/doc/performance.txt)
には、操作・動作中は低品質JPEG、止まった後にlossless refreshする使い方がある。
Automatic Lossless Refreshは設定で有効化し、一定時間更新がなかったクライアントに対し、
対象となる劣化領域を再送する。全領域が無条件に対象ではなく、ALRAll等の設定もある。
ALRは設定によりJPEGでの回復にもできるため、常に数学的な可逆復元とは限らない。

[flowcontrol.c](https://github.com/TurboVNC/turbovnc/blob/ce9585becd8bed42ea568aea1781d704ec9e2a53/unix/Xvnc/programs/Xserver/hw/vnc/flowcontrol.c)
でも、RTT上昇時に送信窓を減らし、正常時に徐々に増やすVegas系の流量制御を確認した。
ただし、その制御だけで短い通信断や長いTCP再送待ちがなくなるわけではない。

### RealVNCとの区別

[公式資料](https://help.realvnc.com/hc/en-us/articles/360002321097-What-can-I-do-to-boost-picture-quality-or-performance)
は回線速度に応じた自動画質調整を説明しているが、内部アルゴリズムまで公開されてはいない。
また[Viewer設定資料](https://help.realvnc.com/hc/en-us/articles/360002254618-RealVNC-Viewer-Parameter-Reference)
には、対象の直接接続でUDPを先に試してTCPへフォールバックするEnableUdpRfbがある。
「VNCは全てTCPだから安定する」とは結論できない。製品、世代、接続方法、拡張の対応を区別する。

## 3周目: 不利になる条件とSunshineへの適用を検証

### VNCでも難しい条件

- 最初の全画面更新、大きなスクロール、全画面動画・パーティクルでは、変更矩形が大きい。
  JPEG中心の方式は動画のフレーム間予測より不利になることもある。
  最近のVNCにはH.264等の対応もあり、全実装をJPEGだけで評価しない。
- TCPは再送して順序を維持するので、欠落を待って表示が停滞する。
  この遅延は、[TCPの順序付き配送・再送仕様](https://www.rfc-editor.org/rfc/rfc9293.html)
  からの帰結であり、接続が維持されても応答性がよいとは限らない。
- 大きな回復更新を一度に送ると、次の操作応答が遅れる。回復更新にも予算が必要。
- 色数低下、JPEG低品質、更新頻度低下は、それぞれ画質・滑らかさとの交換条件。
- 既に送ったTCPデータや圧縮状態に依存する途中データを任意に捨てることはできない。
  古い更新を減らすなら、符号化・送信前に同じ領域の変更を集約する。
- 通信断、経路変更、OSやアプリのタイムアウトは別問題。VNCでも必ず切断を避けられる保証はない。

計算例: 10KiBの更新でも、250kbpsで送る時間は約0.328秒、500kbpsでは約0.164秒。
ヘッダー・暗号・再送・往復待ちは含まない。このサイズは仮定で、VNCの実測値ではない。
小さな矩形だけに絞れることと、大きな更新をためないことの両方が重要。

### 通常Moonlightとの互換性を保つ場合

| VNCから取り入れる考え方 | Sunshine側の実装候補 | 通常Moonlightへの適用 |
| --- | --- | --- |
| 変化が少なければ生成量を減らす | 変更検出、静止時の低頻度送出、符号化前の間引き | 映像形式を保って実装可能。ただし開始時の初回フレーム、復旧、各クライアントの待ち条件を試験する |
| 遅い相手に合わせて更新を集約する | 同じ領域の途中状態を省き、最新画像をエンコードする | 実装候補。既に符号化したPフレームの無条件破棄は避ける |
| 混雑時に新規生成・送出を抑える | 実転送量・RTT・損失に応じた予算、FPS、ペーシング | 既存フィードバックを利用できる範囲で対応。報告がない世代へのフォールバックが必要 |
| 動作中は粗く、停止後に鮮明化 | 変更が収まった領域を、余った予算で段階的に元画質へ戻す | 通常動画として送れる。ただし厳密な可逆更新を意味しない |
| ローカルカーソル | 画像に焼き込むカーソルとクライアントの描画を分ける | 対応クライアント実装が必要。通常iPadでVNC同等の形状同期をホストだけで実現とは言えない |
| CopyRect / パレット / JPEG矩形の直接送信 | 永続キャンバス、矩形受信、更新状態管理を新設 | 通常Moonlightは受け取れない。独自クライアントや別モードが必要 |

現行Sunshineでは src/video.cpp:2436 の静止画最低FPSが、未指定なら要求FPSの半分となる。
要求30fpsなら約15fpsを目指す設定で、基本RFBの「変化がなければ画面更新を待つ」とは異なる。
そのため、背景解像度の低下や更新周期だけでなく、送出頻度・実総量の制御にも改善余地がある。
一方、最低FPSだけを変えても動く画面の上限は下がらず、UDP/FEC等のコストも残る。

先に進める候補は、送受信の計測、実総量に基づく適応制御、静止/変化に応じた符号化前制御、
予算内での画質回復。VNCへの置換は、iPadを含むクライアント・機能・接続方式全体の検討になる。

## 次に実測で比較する条件

実装で確認した工夫がこの環境でどれだけ効くかは、同じ画面と回線で試す必要がある。
この調査では導入・実接続試験を行っていない。

- 同じ2.5K画面で、静止文字、入力、小規模スクロール、全画面スクロール、パーティクルを分ける。
- 音声なし、同じ経路で250/500/1000kbps、遅延増加、単発損失、連続損失、短い通信断を分ける。
- PCのクライアント試験はウィンドウモード。iPadでは実アプリの統計と切断文面を記録する。
- 平均転送量だけでなく、短い区間の最大量、操作から表示までの遅延、読めるまでの時間、
  停止後の画質回復時間、切断数、復帰時間を比較する。
- VNCのパレットとJPEG、Sunshineのコーデック・画質・送出頻度を記録し、
  異なる画質を同じ条件の圧縮率として扱わない。
