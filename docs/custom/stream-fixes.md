# キャレット・背景・クロップの修正

2026-10-15。

## 修正内容

- ChatGPT等のChromium入力欄ではWin32キャレットがなく、TextPattern2/1が返らない構成がある。
  実行中Chromeの読み取り専用調査ではMSAAのOBJID_CARETから位置を取得できた。
  MSAAを取得経路へ追加し、UI Automationでも空選択範囲・空矩形に対応した。
  文字内容は取得せず、見えない位置・別ウィンドウ・古い結果を除外する。
  ログの `Caret focus: position source=msaa` 等で使用経路を確認できる。
- 低帯域モードの既定の上限500kbpsが、4Mbps等の要求も抑えていた。
  `low_bandwidth_target_kbps = 0` を既定に変更し、クライアントが通知したビットレートを使う。
  正の値を設定した場合だけ、その値で上限を指定できる。
  背景自動調整は実効予算3000kbps以上では無効になる。
- クロップ用定数に不変のGPUバッファーを使っていたため、フレームごとの座標更新が反映されていなかった。
  D3D11_USAGE_DEFAULTで生成し、本番とGPUテストで同じ生成関数を使う。
  前回は有効化ログとデコード成功だけで実映像の切り出しを確認したとしてしまい、不十分だった。
  今回は本番の変換処理を通した2フレームの画素をGPUから読み戻して検証した。

## 検証

- ネイティブ360件成功、Web 72件成功。
- 本番D3D変換で2つのクロップ原点の画素を比較。
- 実際のWM_GETOBJECT/IAccessible経路を持つ所有ウィンドウで、キャレット移動・非表示・画面外・別ロールを検証。
- 通常版Moonlight 4.3.1、ウィンドウモード、HEVCで3840×2160から1920×1080へ接続。
- クライアントの500kbps設定は旧クライアントが通知した375kbpsで開始し、背景加工あり。
- 4Mbps設定は同じクライアントが通知した3000kbpsで開始し、背景加工なし。
  サーバーの追加上限は0で、500kbpsへ下げられていない。
- これはローカルループバックでの確認。iPad実機の操作・ChatGPT入力追従そのものの最終確認は未実施。

## クロップを試す条件

PC側を3840×2160などの実解像度にし、iPad/Moonlightではそれより小さい解像度を要求する。
PC側を要求と同じ2560×1920に手動変更した場合は、全画面を等倍で送り、追加クロップは行わない。
サイズ条件を満たさない場合は `Viewport crop bypass ... reason=source_not_larger` を出力する。

配布先は `cmake-build-custom/package-stream-fixes`。共通設定・認証・ペアリングを引き継ぐ。
