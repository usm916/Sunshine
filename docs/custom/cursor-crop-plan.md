# マウス追従の切り出し配信・モニター横断の実装案

作成日: 2026-10-15。単一モニターの切り出しを実装した。現在はユーザー指定に合わせ、大きい辺では各軸 floor(実サイズ / 要求サイズ) + 1 の固定区画へ切り替える。以下の連続追従は当初案として残す。使い方は[viewport-crop.md](viewport-crop.md)。モニター横断は引き続き作業案。

## 目指す動作

PCの4Kデスクトップを維持し、クライアントが要求したFHDまたはカスタム解像度の範囲を、原則等倍で切り出して送る。
出力解像度は接続中に固定する。切り出し位置の移動だけでサーバーやエンコーダーを再起動しない。
映像は従来と同じコーデック・プロトコルで送り、標準Moonlightでも受信できる設計にする。

切り出し枠の中央には、マウスが動いても枠を動かさない矩形の「遊び」を置く。
中央に戻すために毎回枠をジャンプさせず、遊びからはみ出した分だけ枠を動かす。
初期候補は表示幅・高さの約1/3（FHDなら640×360）。値は試験用の開始値であり、推奨実測値ではない。
Web UIで幅×高さを設定し、出力サイズを超えないよう検証する。

- マウスが遊びの内側にいる: 切り出し位置を固定。
- 遊びから出た: 必要な分だけ追従。一定時間後の自動中央戻しは初期仕様に含めない。
- デスクトップの端: 枠を端で止め、マウスが配信画面の端へ近づく。
- カーソルが突然別の場所へ移動した: 見失わない位置へ枠を移す。
- 接続開始時: 現在のマウスが見える位置から開始。

要求解像度が取得できる画面より大きい場合は、等倍を維持して不足部分を黒で埋めるのを初期案とする。
切り出しモードでは、クライアントの要求解像度を物理モニターの解像度へ自動適用しないよう、表示設定との連動も確認する。

## モニター横断の2方式

### 自動切替

マウスがAからBへ移ると、Bの中を切り出して表示する。AとBを同時に1画面へ出さない。
境界に短い滞在時間やヒステリシスを設け、往復による頻繁な切替を抑える。
既存のモニター切替を流用する場合はキャプチャ・エンコーダー再初期化が入るため、一時停止やIDRの増加を計測する。
「接続中に切り替えられる」と「映像が途切れず横断する」は分けて扱う。

### 連続横断

Windowsの仮想デスクトップ座標で切り出し枠を持つ。
枠が境界をまたぐ場合は、AとBそれぞれの必要領域を取得し、クライアント要求サイズの出力画像へ合成する。
全モニターを巨大な映像にして送信する必要はない。
実モニターのない隙間は黒、画面回転は各モニターで補正する。
同一GPU・SDRから着手し、異なるGPU、HDR/SDR混在は追加段階に分ける。

DXGI Desktop Duplicationは出力ごとの取得であり、1つのキャプチャ枠を広げるだけで全モニターを取得できるわけではない。
[Microsoft: DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput)
と[Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)を参照。

## 現行コードを確認して分かった制約

1. キャプチャ: video.cppの非同期キャプチャは選択中の1出力を共有する。mail::switch_displayも全体のイベントで、
   切替時には画像キューの解放と表示の再初期化を行う。接続ごとの追従にそのまま使うと他の視聴接続へ影響する。
2. 入力: make_port/client_to_touchportはモニター全体の縮小・余白を前提にする。切り出し原点と等倍変換を追加する必要がある。
   Windows側には仮想デスクトップ原点を0へ正規化する処理があるため、生の物理カーソル座標と混在させない。
3. 背景: 既存の保持画像はキャプチャ画像の座標で管理される。切り出しが動くたびに保持画像を初期化すると
   背景の大きな更新を招くため、保存位置と描画位置の対応を明示する必要がある。

## 作業の順序

### 1. 単一モニターの切り出しと遊び

- 物理デスクトップ座標、入力用の正規化座標、出力座標を区別する共通データ構造を作る。
- セッションごとに切り出し原点・サイズ・遊びを保持する。
- D3D11の変換前に必要領域をサンプリングし、既存のNVENC出力サイズを維持する。
- 映像で実際に採用した枠を使って絶対座標入力を変換する。丸めやYUV420の整列で差が出ないようにする。
- 既存の低帯域ビットレート/FPS制御と組み合わせる。マウス優先の粗い背景加工とは別の設定にする。

### 2. モニター自動切替と接続ごとの分離

- 安定したモニター識別子、位置、回転、GPUの一覧を管理する。
- 追従先の選択を接続ごとに保持し、別接続の切り出し位置を上書きしない。
- キャプチャ元をモニター単位で共有できるよう管理し、同じ出力の重複取得を抑える。
- 解像度やDPIの違う画面への移動、左側/上側の負座標、抜き差しを扱う。

### 3. 境界の連続合成

- 切り出し枠と各モニターの交差領域だけを固定サイズの出力へ合成する。
- 遅い出力の待機が全配信を止めないようにし、取得失敗時の前画像保持と復旧を決める。
- 最初は同一GPU・SDRで検証。異なるGPUではテクスチャ転送経路を別に設計する。
- HDR/SDR混在では色空間を揃える。接続中にモニターを移っただけで出力形式を変更しない。

## iPad入力と複数接続

相対マウス入力は仮想デスクトップ上の移動として扱える。
直接タッチ・ペン・絶対マウスでは、クライアント位置に切り出し原点を加えてホスト座標へ変換する。
通常の入力パケットはどの映像フレームを見てタッチしたかを持たないので、遅延中の動く枠に対する入力誤差は別途検証する。
初期案では直接タッチの押下から離すまで枠を固定し、ドラッグ中の意図しない追従を避ける。

Windowsの実カーソルとキーボードフォーカスは複数クライアントで共有される。
配信範囲をセッションごとに持つことだけでは、複数人が独立したマウスで同時操作できるようにはならない。
全接続が実カーソルへ追従するか、固定モニター表示を選ぶかは接続ごとに指定する。

将来の文字入力位置への追従は、中心位置の供給元をMouse/Caretへ差し替えられる構造にする。
キャレット取得自体は、この切り出し機能とは分けて実装・検証する。

## 検証と完了条件

- 座標テスト: 遊びの内側/外側、枠の最小移動、四隅、負座標、縦配置、モニターの隙間、サイズ不足、切断/抜き差し。
- 描画テスト: 目盛り画像で等倍、左右モニターの継ぎ目、画面回転、カーソル位置、背景保持と原点移動を画素比較。
- 実接続: 通常版MoonlightとiPad。Windows版の試験は必ずウィンドウモード。
  4K→FHDとカスタム解像度で、クリック・ドラッグ・タッチ・文字入力・モニター横断を確認する。
- 回線: 250/500/1000kbpsで、固定画面・遊び内移動・追従・モニター境界を分け、映像IP/制御/音声の量と遅延・IDR・切断を記録する。
- 接続中に切り出し位置が変わってもホストが再起動せず、関係ない接続の表示が切り替わらないこと。

マウス追従は画面全体のパンを生む。遊びはその頻度を下げるが、通信量の削減を保証しない。
低速回線での比較は、解像度の画素数だけから推定せず実測する。
