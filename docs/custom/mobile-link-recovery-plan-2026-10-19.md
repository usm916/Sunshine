# 移動回線の粗粒化復帰対策案（2026-10-19）

## 推奨方針

減速理由を区別し、回線状態を見ながら映像の送信目標を段階的に上げて確認する。粗粒化の切替には異なる開始・解除条件を設ける。現行の実装・稼働設定はこの検討では変更しない。

## 今回確認できた事実

- 接続5は13:17:18から13:29:45まで継続。ログ上で減速40回、回復140回。100kbpsまで低下し、切断直前は184kbpsだった。
- RTT基準は62msから43msまで下がったが、条件付きの上方更新は0回。最小値への更新は `baseline_revision` に含まれない。送信量超過・エンコーダー再設定停止を示す診断フラグは記録されていない。
- 現行はRTTが基準+max(30ms, 基準の50%)を超えると遅延圧力とする。基準43msなら73ms超、基準52msなら82ms超が対象になる。2窓連続の圧力で目標を25%下げる。
- 回復は10秒の健全期間後にmax(8kbps, 現在値の5%)増加し、以後は約2秒ごと。25%減速を5%刻みで取り返すだけでも6回程度の増速が必要となる。
- `sample_t.loss_events` は未回復データ、IDR/参照フレーム復旧要求、不完全なFEC報告を合算している。ログの `hold_loss` だけで、実際の欠落量・発生理由は区別できない。
- 接続6は再接続後に5Mbpsから開始し、13:30:10にRTT83ms・目標2952kbpsで1/2の粗粒化が有効になった。13:30:21には3099kbps・粗粒化無効の適用ログがある。画面へ反映されたかは未確認。
- 画面サイズは接続6で2560x1920。送信目標、映像圧縮の品質、背景加工と、画面サイズ自体は区別する。

このログは状態変化時の間引き記録であり、全500msサンプルの正確な再生データではない。現実の空き帯域を測定した結果でもない。

## 1. RTT・損失を区別して減速する

RTT上昇、実際の未回復データ、フレーム復旧要求、応答停止、送信予算超過を別々に制御器へ渡す。単発の復旧要求だけで毎回10秒の回復待ちをやり直さない。一定期間の件数・比率・継続時間を確認する。復旧要求を無視するのではなく、反復する場合は減速根拠にする。

RTTは現在の最小値との差に加え、既存のENet RTT変動値と数秒間の増加傾向を見る。遅延だけの短い変動では、増速を一時保留する。遅延だけでの減速を行う場合は継続時間と減速間隔を設け、下げた後にRTTが改善したかを確認する。下げてもRTTが変わらない場合に、同じ理由で毎秒25%下げ続けない。

応答停止、継続した未回復データ、予算超過などの強い証拠には速い減速を維持する。送信量が予算以下という事実だけでは、利用可能帯域が十分とは断定しない。

数値は初期候補として、軽いRTT変動の観測を2〜3秒、遅延だけの再減速間隔を3〜5秒程度から検証する。実損失の制御と同じ閾値にまとめない。

## 2. RTTの基準を現経路へ追従させる

現行の「閾値超えのRTTが10秒連続する」条件では、閾値の上下を行き来する移動回線で候補が消え続ける。低めのRTTと高めのRTTが混在する窓全体を保持し、数十秒間の下位分位値・変動幅を使って経路の基準を見直す。

基準の上方更新は下げた負荷での観測、正常な新規ACK、強い損失や送信予算超過の不在を条件にする。混雑で積み上がった待ち時間を、そのまま新しい正常値として取り込まない。長い観測欠落・不正な報告では更新しない。低い値を一度観測しただけで基準が急低下することも抑える。

## 3. 通常の映像で小さく増速を試し、復帰を速める

正常な新規応答を確認できたら、低予算のまま長く待つ代わりに、既存の映像送信目標を短時間ずつ引き上げる。初期候補は100→200→400kbpsのような低予算域の段階的増加、その後は上限付きの割合増加とする。各段階を観測してから次へ進み、強い損失・応答停滞・遅延の継続増加が出たら直前の安定値へ戻して待つ。

制御ACKが正常なだけでは増やした映像負荷に耐えた証拠にしない。送信・適用状態と実際の送信量も確認する。静止画では送信目標を上げても実通信量が増えないため、その上限を「帯域実測済み」や「安定実績」と記録しない。

過去の安定値を使う場合は、要求値5Mbpsと実際に正常送信できた量を区別する。古い実績を期限なく使わない。初期の検証目標は、回線が健全な試験条件で100kbpsから通常画質まで数十秒程度で戻ることとし、現在の約2分超の増速を短縮する。実回線での時間保証ではない。

## 4. 粗粒化の切替を安定させ、実際の適用状態を確認する

開始・解除の境界を分ける。初期候補は、通常画質からは2500〜2700kbps未満が一定期間続いたときに粗粒化を開始し、粗粒化中は3000kbps以上で実適用を確認して解除する。深刻な悪化では待機を短縮する。

これにより3937→2952kbpsという境界付近の一度の減速で、通常画質から1/2へ切り替わることを抑える。実際に強く帯域を落とす必要がある場合の粗粒化は維持する。音声予約と映像予算の計算も合わせて検証し、境界付近で音声の開始・停止が往復しないようにする。

`focus_enabled` の設定値に加え、GPUで実際に加工したか、カーソル位置不明・画面外・バッファなし等で迂回したかを、状態が変わったときだけ記録する。解除後の静止画でも背景履歴を破棄して通常の画素を出せることをGPU読み戻しで確認する。UACの画面切替も別の試験にし、試験用のログ取得ではUACを出さない。

## 実装順と検証

まず減速理由の分離・RTT処理と、段階的な高速回復を一緒に直し、その後に粗粒化の切替とGPU状態の確認を加える。Sunshineの制御・映像処理が対象で、既存のMoonlightと接続したまま回復することを検証する。

最低限、以下の回帰条件を追加する。

1. 今回のログを参考にした43〜83msのRTT変動と、散発的な復旧要求で最低予算へ張り付かない。
2. 本当に処理しきれない負荷・未回復データ・応答停止では減速し、増速試行が無制限に繰り返されない。
3. 低FPSの送信の山、静止画での低送信量、疎なACK、不正報告・観測欠落を誤った帯域回復の証拠にしない。
4. 健全な試験条件では100kbpsから数十秒程度で通常画質へ戻り、上限を超えない。
5. 3000kbps近辺の往復で粗粒化・音声が頻繁に切り替わらず、解除後の静止画が実際に元の画素へ戻る。

実装する場合は既存の正式テストと新しい回帰テスト、変更行のカバレッジ、GPU確認を通してから部分更新物を作成する。稼働中のTANへの差し替えは別の適用作業として記録する。
