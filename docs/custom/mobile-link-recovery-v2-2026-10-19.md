# 移動回線の回復制御・第2修正（2026-10-19）

[移動試験を基にした対策案](mobile-link-recovery-plan-2026-10-19.md)の実装。対象はWindows/NVENCの低帯域自動モード。

設定場所は **Sunshine Web UI → Configuration → Audio/Videoタブ → Low bandwidth mode → Adaptive bitrate, FPS and background**。既存の設定項目・Moonlightプロトコル・PIN保存先は維持する。

## 変更内容

- 未回復データ、IDR/参照フレーム復旧要求、カウンター未初期化のFEC報告を分離する。未回復データ・制御応答停止・持続的な送信予算超過は、従来の速い25%減速を維持する。
- 単発の復旧要求は1秒の観測待ちにとどめ、健全期間を毎回10秒へ戻さない。要求が連続すると減衰スコアが上がり、減速根拠になる。
- RTTの許容差はmax(45ms, 基準の50%, 上限を設けたENet変動値の4倍)。一時的な超過は増速の保留とし、3秒以上続く場合に10%減速する。遅延だけの減速は4秒以上離して最大2回までとし、負荷を下げても変わらない遅延で最低予算へ落とし続けない。
- RTT基準は固定長64件・直近30秒の履歴から下位20%を使う。10秒以上の継続した観測が必要。上方更新には前の基準から30秒以上経過し、負荷を下げた後または最低予算であることを要求する。実損失・過剰送信・不正報告・観測欠落・FEC回復中は候補を破棄する。大きく揺れた窓も採用しない。
- 正常な新規制御応答と数秒の観測を基に、通常の映像送信目標を段階的に上げる。1000kbps未満では原則2倍、その上は25%・最低128kbps・最大2048kbpsの増加。各段階を3秒観測する。要求上限は超えない。
- 増速試行で悪化すると、直前の目標以下へ戻す。失敗を繰り返した場合の待ち時間は4→8→16→30秒に延ばす。正常な制御応答だけでは帯域の実測成功にしない。十分な実送信量を伴った試行だけを `verified_target_kbps` に記録し、減速時・30秒経過時に無効化する。
- 通常画質から粗粒化へ入る境界は2700kbps未満、粗粒化から通常画質へ戻る境界は3000kbps以上。音声の開始・継続にも同じ境界差を設ける。3000kbps近辺の一度の上下で、画質と音声が往復することを抑える。
- 設定値とは別に、GPUへ渡した加工の状態を `cursor_focus_render` へ記録する。状態変化時のみ、最大2秒に1回。状態は通常画質・バッファなし・位置を対応付けられない・加工有効の4種類。UAC専用の除外は追加しない。

RTT履歴・送信量履歴・診断は固定長で、映像フレームごとのログ出力や外部速度テストは追加しない。試行の通信量は通常の映像の送信目標に含まれる。静止画で実通信量が増えない場合は、目標を上げられても空き帯域を測定できたとは扱わない。

## 診断ログ

**Sunshine Web UI → Troubleshooting → Logs** から確認する。

`low_bandwidth_state` に、`unrecovered_packets`、`frame_loss_requests`、`incomplete_reports`、`probe_active`、`verified_target_kbps` を追加した。元の `hold_loss` は未回復データまたは繰り返す復旧要求による圧力を示す。

`cursor_focus_render` の `reason` は0=通常画質、1=バッファなし、2=有効な位置なし、3=GPUの加工定数が有効。`applied` はシェーダーへ有効な定数を渡したことを示し、遠隔端末の表示結果を直接測った値ではない。表示品質の確認には実画面の試験も必要。

## 検証

制御器の独立テスト36件で、今回に近い43〜83msの揺れと散発的な復旧要求、低FPSの送信の山、強い継続損失、無応答、不正報告、失敗試行の巻き戻しと再試行間隔、静止画での未確認帯域、履歴の期限切れ、2700/3000kbpsの境界を検証した。制御ヘッダーの実行行235/235を実行した。

全500msサンプルがログに残っているわけではないため、現実のログそのものの完全再生とは区別する。同じ合成条件で旧・新版を比較し、旧版は100kbpsに残った条件で、新版は回線回復後19.5秒で3000kbps以上へ到達した。別の合成条件ではRTTの揺れ・単発の復旧要求だけで送信目標を落とさなかった。

正式な本体組み込みテスト426件／54スイートが成功。変更した本体コードの実行行155/155を実行した（今回の作業前コピーとの差分。全プロジェクトや全分岐の100%ではない）。GPU読み戻しでは、入力画像が変化していなくても低画質プロファイルから通常プロファイルへ戻すと元の画素に戻ることを確認した。

隔離したループバック接続で、受信側を4秒停止してから再開した。送信目標3000→2250→2025→2531→3000kbps、GPU加工有効→無効を同じ接続で確認した。端末はWindowsの試験クライアントであり、iPadや実WANでの確認ではない。

検証記録は `cmake-build-mobile-recovery-v2/`。実回線で同じ復帰時間になることを保証する結果ではない。
