# 移動回線で粗粒化が戻らない問題の監査（2026-10-18）

本書は修正前の監査記録。実装と検証結果は [recovery-fix-2026-10-18.md](recovery-fix-2026-10-18.md) を参照。

電車で駅→移動→駅と移動し、回線悪化で粗粒化、到着後約1分待っても戻らず、再接続すると解除されたという実機報告を対象とする。接続先はTANと思われるが未確定。今回の制御ログは未取得で、TANのサービス標準出力 `C:\Windows\Temp\SunshineCustomService.log` は現在の実行権限では読み取りを拒否された。以下は現行製品コードを用いて再現した問題と、実事象では未確定の部分を区別する。

## 結論

現行の自動低帯域制御に、低FPSの送信の山で回復が止まる問題と、経路変更後の安定したRTTを混雑と見なし続ける問題がある。どちらも再接続で状態が初期化されると一時的に解除される。今回の列車移動がどちらの条件だったかはログから確定していない。正常な回復でも、最低予算まで下がった場合は約1分では粗粒化が解除されない。

## 帯域をどう判断しているか

実際の利用可能帯域を速度テストで測定してはいない。`src/stream.cpp:1294` 付近で500msごとに、送信したメディアIPバイト数、ENetの平滑化制御RTTと新規ACK時刻、FEC回復・欠落・参照復旧要求を集計する。送信量は受信成功量ではない。

`src/video_low_bandwidth.h:155` の制御器は次を圧力として扱う。

- 欠落・復旧要求がある。
- 新規RTTが接続中の最小RTT＋max(30ms, 最小RTT/2)を超える。
- 新規の正のRTT観測が2秒ない。
- 直近の送信量が現在予算の120%を超える。FEC回復があり予算超過の場合も含む。

連続2窓の圧力で予算を25%下げる。圧力、不正な報告、1500ms超の計測間隔は10秒の健全期間をリセットする。10秒の健全期間後、新規の正のRTTが届く時だけ、約2秒ごとにmax(8kbps, 現予算の5%)上げる。回復上限は接続時のクライアント要求とサーバー上限。粗粒化解除はセッション予算3000kbps以上。

RTTは映像フレーム間隔ではなくENetの送信とACKの時刻差で更新される（`third-party/moonlight-common-c/enet/protocol.c:869`）。既定PING間隔500msも映像FPSと別である。したがって「低FPSをRTT基準に採用する」という直接の処理はない。ただし低FPSによる送信量の偏りは回復判定に入る。

## 再現1：1fpsの送信量を過剰送信と誤判定

製品と同じ `controller_t` と `make_profile()` を使い、4Mbpsから損失を与えて100kbps・1fpsへ下げた。以後はRTT40msで毎窓新規ACK、損失0の入力とした。500ms窓に180kbps・0kbpsを交互に与えると、平均送信量は90kbpsで100kbps予算以下なのに、180kbps側が120%条件を満たして健全期間を毎秒リセットする。3分与えても100kbpsのままで粗粒化が戻らなかった。対照として毎窓90kbpsなら最終的に4Mbpsへ回復した。

送信側は1枚の全IPバイト数をフレーム送出完了後にまとめてatomic加算する（`src/stream.cpp:2215`）。この集計は低FPSで偏りやすい。TAN保存設定の最小FPSも1だった。

## 再現2：経路変更後のRTTを永久に過大判定

最初のRTT20ms、その後は損失0・送信量0・毎回新規ACK・一定80msとして180秒与えた。基準は接続中の最小値20msから上がらないため、80msが毎回「遅延増加」になる。予算は100kbpsへ下がり続け、回復しなかった。同じ80msで再接続相当のinitializeを行うと4Mbps・粗粒化なしに戻った。

これは経路RTT変化の制御上の再現であり、実際の回線容量が増えたことの測定ではない。移動回線の経路変更と混雑を区別する仕組みが必要。

## 約1分待った場合

100kbpsまで下がった後、送信量90kbps・RTT40ms・欠落0・新規ACKを500msごとに与える理想化した条件でも、60秒後は382kbps。粗粒化解除の3Mbps到達まで146秒かかった。上限4Mbpsまでの回復はさらに後になる。最低まで下がっていた場合、1分待って変わらないことは現行回復速度でも説明できる。

8秒ごとに1回だけ欠落通知を与えた試験でも、連続10秒の健全期間が成立せず回復しなかった。制御上は意図された保守性だが、移動回線での使い勝手との調整が必要。

## 再接続すると解除される理由

接続開始時に目標予算を要求上限へ戻し、RTT基準、健全期間、欠落カウント、エンコーダー再設定状態を新規作成する。そのため、再接続で鮮明になったことだけでは帯域が回復した証明にはならない。新しいセッションが高い予算から再開した結果でも同じ表示になる。

## 余分な処理・他の停止経路

- 低帯域モード中、通常のadaptive_bitrate制御器は無効化されており、二重にビットレートを下げる構成ではなかった（`src/stream.cpp:2825`）。
- 背景保持画像は加工前の画素を保持する。回復した予算を適用すれば、粗さを戻し、3Mbps以上で元の入力画素へ切り替えられる。既存GPUテストも成功した。
- 一度でもエンコーダー再設定が失敗・非対応になると `reconfigure_status=-1` になり、以後の自動制御全体を停止する（`src/video.cpp:117`、`src/stream.cpp:1316`）。再接続で解除される別の経路である。今回これが起きた証拠はない。
- フレーム内の送信ペーシングは約800Mbps相当の既存値（`src/stream.cpp:2037`）であり、低速WANの容量に合わせたパケット分散ではない。フレーム間の待機はあるが、1枚の短時間集中がなくなるわけではない。これが今回の混雑原因だったと確定してはいない。
- 最小FPSを守るための更新・制御ACK・FEC自体は維持する目的がある。単に停止すれば回復が良くなるとは言えない。今回確認した問題の中心は余分な画像加工ではなく、測定の粒度と回復条件である。
- 低帯域の自動モードは背景加工をセッション内で有効にする。保存済みのマウス優先設定が無効でも、予算低下で背景加工が入る。保存設定の書き換えとは別である。

## 修正の優先順位

1. 500ms単窓の送信量だけで回復を阻止せず、低FPSのフレーム間隔を含む集計と持続的な過剰送出を使う。受信側の損失・遅延との区別を保つ。
2. 接続中最小RTTへの永久固定を見直し、経路変更と一時的なキュー遅延を区別しながら基準値を更新する。単に高RTTを正常扱いするだけの変更は避ける。
3. 上向き試行の速度と、まれな欠落で毎回10秒をやり直す条件を調整する。無条件で要求上限へ戻す方式にはしない。
4. baseline、送信平均、ACK鮮度、健全期間、判定理由、再設定停止理由を、状態が変わる時に記録する。不要なログ量を増やさず実WANで原因を区別できるようにする。

本番C++ソース、設定、実サービス、配布バイナリは今回変更していない。これは修正版の配布報告ではなく、実装監査と再現結果である。
